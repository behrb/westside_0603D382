# Escalation Alert Prediction — пошаговая инструкция

## Статус: решение уже прогнано на ваших реальных файлах

- **OOF ROC-AUC ≈ 0.598** (5-fold Stratified K-Fold, LightGBM).
- `submission.csv` в этой папке — уже готовый файл с предсказаниями
  (колонки `signal_id`, `ehtimollik`), можно отправлять как есть или
  улучшать дальше.
- `solution.ipynb` уже выполнен от начала до конца на ваших данных — там
  внутри реальные графики и цифры, ничего запускать не обязательно, но можно
  перезапустить и поменять что-то своё.

## Что в этой папке

- `solution.ipynb` — полный пайплайн: загрузка данных → EDA → feature engineering →
  валидация модели → предсказание → `submission.csv`. Открывается в VS Code
  или Jupyter. Уже выполнен на ваших данных.
- `eda_app.py` — рабочий EDA-сайт на Streamlit (второй обязательный дедлайн),
  уже заполнен реальными наблюдениями по вашим данным, проверен и запускается
  без ошибок.
- `submission.csv` — готовый файл для отправки на лидерборд.
- `requirements.txt` — все зависимости.
- `data/` — сюда нужно положить файлы соревнования, если захотите перезапустить
  ноутбук (в этой папке для скачивания сами данные не включены — они у вас уже есть).

## Шаг 1. Установка окружения

В VS Code откройте терминал в этой папке и выполните:

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

В VS Code выберите этот `.venv` как интерпретатор для ноутбука (`Ctrl+Shift+P` →
"Python: Select Interpreter").

## Шаг 2. Данные

Создайте папку `data/` рядом с ноутбуком и положите туда файлы соревнования
ровно с этими именами:

```
data/
  train_signals.csv
  train_transactions.parquet
  test_signals.csv
  test_transactions.parquet
  sample_submission.csv
```

## Шаг 3. Запуск ноутбука

Откройте `solution.ipynb` в VS Code (или `jupyter notebook solution.ipynb`) и
выполняйте ячейки по порядку сверху вниз ("Run All" тоже подойдёт после
первого прогона). В конце появится файл `submission.csv` в этой же папке —
это и есть файл для отправки на лидерборд.

Каждый крупный шаг в ноутбуке подписан markdown-ячейкой с объяснением, зачем
он нужен — этого достаточно, чтобы разобраться и при необходимости объяснить
решение на защите.

## Шаг 4. Улучшение модели (по желанию, но сильно влияет на место в рейтинге)

Смотрите раздел "Что можно улучшить дальше" в конце ноутбука. Самое дешёвое
по усилиям и обычно самое эффективное:
1. Добавить признаки часа/дня недели транзакции.
2. Расширить набор окон агрегации (не только 1/3/7/30 дней).
3. Подобрать гиперпараметры LightGBM (`num_leaves`, `learning_rate`,
   `n_estimators`) по OOF ROC-AUC из ноутбука.

## Шаг 5. EDA-сайт (обязательный второй дедлайн)

1. Дополните `eda_app.py` реальными графиками и текстовыми выводами по вашим
   данным (в файле оставлены комментарии-подсказки, что именно вписать).
2. Проверьте локально:
   ```bash
   streamlit run eda_app.py
   ```
3. Задеплойте бесплатно на Streamlit Community Cloud:
   - Залейте папку в **публичный** репозиторий на GitHub (включая
     `requirements.txt`, но данные в `data/` из соображений размера и
     конфиденциальности в репозиторий класть не обязательно — организаторы
     проверяют сайт, а не то, что он умеет читать реальные файлы).
   - Зайдите на https://share.streamlit.io , подключите GitHub, выберите
     репозиторий и файл `eda_app.py`.
   - Получите публичный URL вида `https://<app-name>.streamlit.app` — это и
     есть ссылка, которую нужно сдать организаторам.
   - Альтернатива без Streamlit: собрать статичный HTML-отчёт (например,
     через `nbconvert` из ноутбука с графиками) и захостить на **GitHub
     Pages** или **Vercel/Netlify** — тоже полностью укладывается в
     требования задания ("любая технология").

## Шаг 6. Финальная проверка перед сдачей

- [ ] `submission.csv` содержит те же `signal_id` и в том же порядке, что и
      `sample_submission.csv`.
- [ ] Все предсказания — вещественные числа от 0 до 1 (не 0/1 метки).
- [ ] Нет пропусков в колонке с предсказанием.
- [ ] EDA-сайт открывается по публичной ссылке без входа в чужой аккаунт.
- [ ] На сайте есть все 7 обязательных пунктов из условия задания (описание
      подхода, обзор данных, визуализации, наблюдения, анализ таргета,
      признаки/идеи из EDA, выводы).

## Что показал анализ реальных данных

- В train 14 000 алертов, в test — 6 000. У каждого алерта есть история
  транзакций (в среднем ~499 транзакций на алерт), пропусков в данных нет.
- Классы несбалансированы: 82.8% отклонено, 17.2% эскалировано.
- `miqdor_indeksi` — стандартизированный индекс размера транзакции, может быть
  **отрицательным** (это не сырая сумма в деньгах) — поэтому в признаках важно
  использовать и сырое значение, и модуль (`abs_amount_*`).
- Различия между эскалированными и отклонёнными алертами по отдельным
  агрегатам небольшие (например, среднее число транзакций 523.8 против 494.0,
  доли по типам почти одинаковые) — сигнал слабый и распределён по многим
  признакам, поэтому градиентный бустинг с широким набором признаков
  оправдан больше, чем простые правила.
- Самые важные признаки по `feature_importances_`: `amount_min`,
  `type_amt_naqd`, `kirim_ratio`, `amount_max`, `night_share`, `naqd_ratio`,
  `xalqaro_ratio` — редкие типы транзакций (`naqd`, `xalqaro`) оказались
  на удивление информативны, несмотря на малую долю в объёме.

## Как ещё поднять ROC-AUC (конкретно под ваши данные)

1. **Подбор гиперпараметров через Optuna** — текущие параметры LightGBM
   подобраны вручную, автоматический подбор (num_leaves, learning_rate,
   min_child_samples, reg_lambda/reg_alpha) обычно даёт +0.01-0.03 AUC.
2. **Признаки "аномальности относительно своей же истории"** — например,
   z-score последней транзакции относительно среднего и std по истории того
   же `signal_id` (сейчас есть признаки на уровне всего окна, но нет
   "насколько последняя транзакция необычна именно для этого клиента").
3. **Blending моделей** — усреднить предсказания LightGBM с логистической
   регрессией на масштабированных признаках или CatBoost — часто даёт
   небольшой, но стабильный прирост.
4. **Более гранулярные окна для `naqd`/`xalqaro`** — раз именно эти признаки
   оказались важны, стоит посчитать их отдельно для разных окон (1/7/30 дней),
   а не только по всей истории.
5. **Feature selection** — попробовать оставить только топ-30 признаков по
   важности и сравнить OOF AUC — иногда шумные признаки немного мешают.
